# Lean recording for the BO-06 research replay

The user approved the measurement proposal in `bo-06-readiness/measurement-decision.md`
with “Si claro”. This record supersedes that proposal's pending status. It does
not change the recorded outcomes of the earlier precision and observation tests.

`P_LEAN_RESEARCH_V1` uses the existing version 2 replay contract, with these
explicit amendments: the Java phase agent is absent, the lean task/output
recorder remains on both arms, and external process sampling is diagnostic.
The former 100 ms recorder-imbalance and 500 ms sample-gap admission rules do
not qualify this mode. Their previous failures remain failures.

The request clock, source identity, owned state, process cleanup, native CPU
mask and complete output comparisons are unchanged. Recording time is not
subtracted. The result describes the declared workflow with recording enabled;
it cannot establish an equivalent saving for ordinary, uninstrumented Gradle.
That comparison remains part of BO-09.

A mode-specific receipt is required for owner execution. Local consuming-path
qualification admits the control; a passing control admits the development
prefix; both passing trials are needed for confirmation admission. The receipt
binds the implementation, workflow, local proof, trial results and closed
processes. An old overhead receipt cannot stand in for it.

Run one identical-code control on original revisions17–20. Revision17 is cold;
18–20 are measured. Each arm has its own state and the same supported V2
correction. Run eight builds with alternating order, four live and four
independent comparisons. Stop if correctness or required evidence fails, or
if the absolute measured total difference is both at least three seconds and
at least 5% of the faster arm. Keep the cold results and every host flag.

Only after a pass, run one native/corrected sequence from anchor0 through20:
42 builds,21 live and21 independent comparisons. Preserve state within each
arm. Across all20 non-cold slots require at least5% and one second saved per
scheduled change after required work outside the request. Retain cold and
preparation costs. A negative result, mismatch or unexplained harness failure
ends this allocation. Do not repair the implementation during a trial.

The combined owner limit is50 builds,50 standalone comparison JVMs,ten elapsed
hours,80GiB of new state and at least40GiB free disk. Each build has900 seconds.
Failures count. There are no retries or extra CPU profiles. Local fixture
qualification has a separate ceiling recorded before execution:104 fixture
workflows,zero owner builds or JVMs,30 minutes,2GiB and16 test/build commands.

If both owner trials pass, freeze the final implementation and propose BO-07
limits from observed time and disk use. Do not start protected changes21–100.
The original material-saving, repetition, coverage, correctness, cost recovery,
statistical and tail criteria remain unchanged for that later decision.
