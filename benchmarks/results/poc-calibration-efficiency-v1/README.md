# Calibration efficiency result

This bundle is the terminal evidence for
`POC-CALIBRATION-EFFICIENCY-001`. It evaluates the same six qualified source
cells as the prior calibration-economics study under the preregistered
[`poc-calibration-efficiency-v1`](../../../specs/poc-calibration-efficiency-v1.md)
protocol.

The implementation makes three bounded changes: it derives the original and
candidate structural state in one Gradle discovery, replays a proposal only
when every declared input and generated artifact has the same digest, and
stops candidate target stabilization after two exact matching task-outcome
fingerprints. The native control still uses all three warm-ups. Existing
terminal build observations, savings, output equivalence and fallback evidence
are unchanged.

## Result

| Workflow and change | Cold discovery before -> after | Exact replay | Installed break-even | Full POC break-even |
| --- | ---: | ---: | ---: | ---: |
| Groovy `jar`, leaf source | 257.822 -> 226.060 s (**12.32% less**) | 0.281 s | **10 -> 9 builds** | **20 -> 19 builds** |
| Groovy `jar`, shared source | 285.874 -> 262.989 s (**8.01% less**) | 0.297 s | **11 -> 10 builds** | **22 -> 21 builds** |
| Kafka Checkstyle, metadata source | 364.764 -> 312.591 s (**14.30% less**) | 0.330 s | **31 -> 26 builds** | **55 -> 50 builds** |
| Kafka Checkstyle, client-utils source | 358.817 -> 329.099 s (**8.28% less**) | 1.261 s | **27 -> 24 builds** | **49 -> 46 builds** |
| Kafka `shadowJar`, clients source | 269.760 -> 212.906 s (**21.08% less**) | 0.323 s | **15 -> 13 builds** | **28 -> 26 builds** |
| Kafka `shadowJar`, generator source | 264.598 -> 231.906 s (**12.36% less**) | 0.561 s | **14 -> 13 builds** | **27 -> 25 builds** |

Every cell improves installed and full-POC break-even. Cold structural work is
8.01% to 21.08% lower, while an exact repeated proposal takes 0.281 to 1.261
seconds. A repeat evaluation that still reruns the two required candidate
target warm-ups repays after 4, 5, 12, 11, 5 and 5 qualifying builds
respectively; replay does not remove the need to remeasure a changed target.

## Evidence and integrity

- Each cell has two fresh cold proposals and two exact replays.
- The output contract, manifest, graph, generated binding, fallback input and
  proposal are byte-identical between cold and replay paths.
- Adding one Gradle option misses the cache and fails closed in all 12
  captures.
- Both historical terminal captures per cell have three identical non-empty
  candidate target fingerprints. The third execution independently confirms
  that the two-execution early stop would have been safe for these captures.
- The terminal mean saving is copied unchanged from the qualified
  change-breadth evidence; no build-time percentage is remeasured or rewritten.
- [`summary.json`](./summary.json) is regenerated byte for byte by the strict
  checker from the 12 phase records and immutable terminal sources.

Validate the complete bundle and its negative tamper fixtures with:

```bash
./dev/check-calibration-efficiency-result
./dev/test-calibration-efficiency-result
```

## Interpretation

This result improves the economics of validating a structural profile; it is
not itself a customer build-speed claim. A first evaluation still needs real
Gradle output preflight/discovery and two candidate target warm-ups. Exact
replay is useful only while the repository, revisions, changed paths, owner
inputs, output policy, Wrapper, Gradle options, generated state and BuildOpt
binary remain identical. Any drift returns to discovery or native Gradle.

No automatic activation, production authorization, repository-name rule,
public-service expectation, soak, design-partner dependency or Test
Optimization scope is introduced.
