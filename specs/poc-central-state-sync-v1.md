# Central BuildOpt state synchronization POC

## Purpose

This contract proves that generated BuildOpt optimization memory can move
between independent checkouts through the existing owner-operated HTTPS state
service. It covers qualified profile portfolios, their evidence and resumable
optimization checkpoints. It does not make a build depend on that service and
does not authorize a remote profile for execution.

The machine-readable contract is
[`poc-central-state-sync-v1.json`](./poc-central-state-sync-v1.json). The
executable proof is [`dev/check-central-state-sync`](../dev/check-central-state-sync).

## Customer surface

Connect a repository once:

```bash
buildopt connect https://buildopt.example.com \
  --token-file ./buildopt.token \
  --ca-file ./buildopt-ca.pem
```

Synchronize explicitly when needed:

```bash
buildopt sync
```

`connect` derives the repository identity, verifies the HTTPS endpoint and
token scope, copies credentials into the private repository-local connection
directory and immediately performs the first sync. `sync` reuses that exact
connection. Neither command requires a hand-authored portfolio, evidence file
or checkpoint: it only publishes state already generated by `buildopt optimize`.

The connection is stored below `.buildopt/central/v1`. The bearer token is
never passed to Gradle and never appears in the JSON result.

## Exact state boundary

Each state kind is transported as one canonical
`buildopt.poc/central-state-bundle/v1` document. Every bundled file has a
relative path, schema version, byte length and SHA-256. Portfolio entries are
accepted only when their manifest, graph, generated manifest, evidence and
profile bytes match the digests recorded in the portfolio index.

Publication preserves the server contract:

1. upload the immutable bundle object;
2. upload the immutable typed manifest;
3. advance the kind head with the exact prior generation and head digest.

Evidence is processed before portfolios, and a portfolio manifest references
the exact evidence manifest that qualified it. Checkpoints remain separately
typed and expire after 24 hours.

## Conflict, retry and offline behavior

- Repeating an unchanged sync uploads nothing and reports `NO_CHANGE`.
- A partial object or manifest upload is invisible until its head advances;
  retrying uses the same digests and completes the interrupted generation.
- Competing writers may conflict while reserving a manifest generation or
  while advancing the head. The loser waits only for the bounded winning
  generation, verifies it and reports `CONCURRENT_REMOTE_WON`.
- A newer remote generation is retained. An older incompatible local state
  never replaces it and the result requests native fallback.
- Each successful online operation stores bundle, manifest and head bytes as
  a private snapshot. During an outage, only a snapshot whose canonical form,
  digests, scope, kind, generation and cross-document bindings all verify may
  be used. A modified snapshot reports `OFFLINE_NO_SNAPSHOT`.

## POC boundary

This block proves exact movement and recovery of optimization memory. By
itself it does not authorize a remote profile. The later
[central optimize integration](./poc-central-optimize-integration-v1.md) now
performs the required local revalidation and automatic pre/post sync. Automatic
remote Gradle-cache configuration, two-machine installed behavior and a
central wall-time claim remain later blocks. Production HA, RBAC, KMS, backups,
soak testing and Test Optimization are outside this POC.

## Verification

```bash
./dev/check-central-state-sync
```

The race-enabled integration starts the real TLS handler and exercises first
sync, no-change sync, a clean consumer, incompatible-state fallback,
interrupted publication and exact retry, concurrent writers, verified offline
reuse and corrupt-snapshot rejection.
