# Ktor new-family change-breadth experiment

## Question

Does the Ktor JVM JAR result remain correct and valuable for materially
different change classes when BuildOpt uses the same generic owner-input,
structural proposal, exact-output and native-fallback path?

## Frozen subject and cells

Ktor remains fixed at public revision
`bc7de799f4eb997a63250f2f70492d85f5c92f50`, Gradle 9.5.1, Temurin 21 and
the public unqualified `jvmJar` selector. The terminal source-only transfer is
prior evidence; none of its timings can be reused here.

Four independent cells are frozen before any new proposal or timing:

1. an upstream `ktor-utils` production-source change with both the dependency
   and `ktor-http` consumer JARs declared;
2. a real JVM service resource change in `ktor-server-core`;
3. a mixed production-source change spanning `ktor-http` and
   `ktor-server-core`, with both JARs declared; and
4. a root `gradle.properties` change that must retain the native full graph
   and is never timed.

Every path, original SHA-256, deterministic mutation, required output and
expected structural entrypoint is recorded in
[`poc-new-family-change-breadth-v1.json`](./poc-new-family-change-breadth-v1.json).
Expected entrypoints are derived from the already reviewed Gradle output
owners, not from observed timing. The implementation must contain no Ktor or
repository-name decision branch.

## Value and fallback rules

Each complete selective cell receives two fresh eight-pair captures. Adjacent
opposite orders form eight reciprocal blocks. Qualification requires at least
500 ms and 2% mean saving, a positive median and deterministic 95% lower
bound, at least six positive blocks, non-regressive p95, byte-identical
required outputs, stable task shapes, two successful full-graph fallbacks and
zero product-attributable failures.

The global cell receives two independent installed-path proposals. Both must
return `NATIVE_FULL_GRAPH / GLOBAL_CHANGE_REQUIRES_FULL_GRAPH`, emit no
candidate documents and make no timing claim. Any selective cell whose graph
or outputs are incomplete also retains optimized native Gradle; it is not
discarded or converted into a favorable percentage.

## POC boundary

This experiment tests change breadth for one public JVM JAR workflow. It does
not claim Ktor release-build coverage, authorize automatic or production
activation, alter Test Optimization, require a soak or depend on a design
partner. Percentages remain cell-specific and are never added or averaged.

Validate the frozen contract before running any proposal:

```bash
./dev/check-new-family-change-breadth --spec-only
```

## Recorded runner correction

The first complete diagnostic matrix on BuildOpt `980d021` exposed that the
generic matrix runner used its common Gradle option list and did not propagate
the already preregistered Ktor property
`-Pktor.develocity.skipBuildScans=true`. Both arms were internally comparable,
but the run does not satisfy this frozen contract. All 48 diagnostic pairs are
preserved under the incident path recorded in the machine specification and
none may enter terminal aggregation.

The generic runner now consumes `method.gradleOptions` exactly when present
and retains its previous defaults for older specifications. No cell, input,
output, option, threshold, order, fallback or POC boundary changed. Terminal
captures restart from zero on the correction revision.
