# Cross-commit breadth replication

## Purpose

`POC-CROSS-COMMIT-BREADTH-REPLICATION-001` applies the Kafka recovery path to
additional public Gradle families without changing eligibility, refresh,
transport, exact-output or fallback behavior. A subject can broaden the claim
only when a later public commit selects the profile, preserves required output
bytes and has positive attributable replay value.

The original machine preregistration freezes Spring Framework root `classes`
and the OpenTelemetry JMX `testClasses` family. After the Spring target exposed
a broad mixed-source closure, an independent Spring JMS addendum froze a
lower-closure owner and two direct public descendants before any JMS timing.
The original contract is never rewritten after observation.

## Method

Every qualification uses one useful warm-up plus eight alternating
control/candidate pairs, a fresh Gradle process per build, persistent Wrapper
and dependency caches, at least seven positive pairs, a positive paired
interval, non-regressive p95, exact fallback and a maximum 30-build break-even.

Qualified subjects must additionally pass an independent-root native output
portability gate before any descendant timing. Lifetime observations keep
selected replay saving separate from native-retained arm variation. A native
output mismatch is retained as evidence and grants no performance claim.

## Frozen findings

- Spring root `classes` discovers a 21/27-project mixed-source candidate but
  loses 206.25 ms on average, has 1/8 positive pairs and fails calibration.
- OpenTelemetry completes 17 ordinary invocations but a mixed commit combines
  three JMX library paths with an unowned root `CHANGELOG.md`; discovery fails
  closed as `SOURCE_OWNERSHIP_AMBIGUOUS` before calibration.
- Spring JMS discovers a 10/27-project candidate and saves 2,590.375 ms or
  11.43% with 8/8 positive pairs. Independent native roots differ in 14 of
  8,385 class files, so portability rejects the profile before replay.

The terminal decision is `DO_NOT_BROADEN_CROSS_COMMIT_VALUE_CLAIM`. The
positive Kafka replay remains the only checked cross-commit value claim.

## Recovery hypotheses

Follow-up work may test only repository-independent mechanisms:

1. bind unowned-path relevance to the observed Gradle workflow input model;
2. detect native-volatile output producers before transport, exclude their
   bytes from the pack and execute them locally; and
3. choose descendant windows by frozen structural compatibility, including a
   refresh commit followed by an omitted-owner change.

Exact bytes remain mandatory for every output BuildOpt transports or reuses.
The POC may not normalize customer bytecode, ignore a mismatch by extension or
select a favorable commit after timing.

## Boundaries

repository-name rule, averaged repository percentage, soak/design-partner
requirement or Test Optimization behavior.
